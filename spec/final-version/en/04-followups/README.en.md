# Spec FV03.1–FV03.7: Follow-Up Specs Index

中文版：[../../zh-CN/04-followups/README.zh-CN.md](../../zh-CN/04-followups/README.zh-CN.md)

These seven specs turn the [04-followups system design set](../../../../system_design/final-version/en/04-followups/README.en.md) into testable requirements, following this project's SDD+TDD convention: every functional requirement (FR-) has at least one acceptance criterion (AC-) and at least one test case (TC-), and every test case traces back to a requirement. Requirement IDs continue parent [Spec FV-03: Embedding and Vector RAG](../03-embedding-vector-rag.spec.en.md)'s own numbering — `FR-FV03-014` through `FR-FV03-043`, `NFR-FV03-005` through `NFR-FV03-018`, `AC-FV03-009` through `AC-FV03-047`, `TC-FV03-015` through `TC-FV03-074` — continuing directly from that spec's highest existing IDs (`FR-FV03-013`, `NFR-FV03-004`, `AC-FV03-008`, `TC-FV03-014`), the same convention the [10-followups spec set](../10-followups/README.en.md) uses relative to parent Spec FV-10.

Build order is mandatory, not just a numbering convention — each spec depends on the previous one's output:

1. [Spec FV03.1: Unifying the Vector-Only and Hybrid Retrieval Paths, and Wiring in Real Embeddings](01-unifying-the-vector-and-hybrid-retrieval-paths.spec.en.md) — build first. Makes the hybrid-scoring path (not the vector-only path) the only one reachable from a live chat query, and gives it a real `EmbeddingClient`. Every other spec in this set assumes this path is canonical. **Implemented.**
2. [Spec FV03.2: Replacing Jaccard Keyword Overlap with Real BM25 Scoring](02-bm25-keyword-scoring.spec.en.md) — depends on FV03.1 (the `vector_score` term it fuses with must already be real, or a BM25 upgrade to the keyword term alone cannot be meaningfully evaluated). **Implemented.**
3. [Spec FV03.3: Adding a Real Cross-Encoder Rerank Stage](03-cross-encoder-reranking.spec.en.md) — depends on FV03.1/FV03.2's candidate ordering; reranks whatever those two specs already rank, without changing their scoring. **Implemented**, including against the real `BAAI/bge-reranker-base` model, not only fakes.
4. [Spec FV03.4: A Golden Dataset and Automated Hit Rate / MRR Evaluation for Retrieval](04-golden-dataset-hit-rate-and-mrr-evaluation.spec.en.md) — depends on FV03.1–FV03.3 producing a stable pipeline to evaluate; run against the pre-FV03.1 pipeline, its Hit Rate/MRR numbers would describe a system this platform no longer runs. **Implemented**, with a 50-case Golden Dataset (§9 of its own implementation records one label correction found by actually running retrieval against it, not by trusting the labels) — later replaced by FV03.6's real 24-case dataset.
5. [Spec FV03.5: Production Vector Search with pgvector](05-pgvector-production-vector-search.spec.en.md) — depends on FV03.1–FV03.4 as a stable foundation; its own source design's §1 records a schema-targeting correction made only after FV03.1–FV03.4 landed, which is why this spec was deliberately sequenced last rather than written speculatively ahead of the others. **Implemented.**
6. [Spec FV03.6: A Real-Business Golden Dataset, and an Embedding-Reload Efficiency Fix](06-real-golden-dataset-and-embedding-reload-fix.spec.en.md) — a code-review follow-up to FV03.1–FV03.5: fixes `_load_knowledge_store_from_db()` recomputing every chunk's embedding on every restart instead of reading FV03.5's backfilled vector, and replaces FV03.4's synthetic 50-case fixture with a real, schema-grounded, self-verified 24-question Golden Dataset stored as data (`golden_dataset/cases.json`), not Python literals. **Implemented.**
7. [Spec FV03.7: Durable Observability Storage for Golden Dataset Mining](07-durable-observability-storage-for-golden-dataset-mining.spec.en.md) — depends on FV03.6's `golden_dataset_mining.py`, whose mechanism could only mine questions asked during the current process's uptime since the observability log/trace stores it reads are in-memory only; this spec adds a Postgres-backed, pooled, retention-swept implementation of both. **Implemented.**

## Status

All seven (FV03.1–FV03.7) are fully decided and implemented, with acceptance criteria, test plans, and traceability matrices. They were written after a request to turn the [04-followups design series](../../../../system_design/final-version/en/04-followups/README.en.md) into testable requirements at the same rigor level as the [10-followups spec set](../10-followups/README.en.md), rather than leaving them as prose design documents. Each spec's own §9 Implementation Notes records the judgment calls made while writing it down — for example, FV03.1's decision to keep `InMemoryVectorRagRetriever` in the codebase rather than delete it (§9), FV03.2's explanation of why a persistent BM25 index was deliberately rejected in favor of a per-request one scoped to the caller's own permission-filtered candidates (§9), FV03.3's note on why its exception handling is intentionally broad (§9), FV03.4's explicit statement that no test case can substitute for a human correctly labeling the Golden Dataset's ground truth (§9), FV03.5's two named, deliberately-out-of-scope limitations (shared-visibility SQL support, and the still-open corpus-in-memory-at-startup scaling ceiling pgvector alone does not remove — §9), FV03.6's note that its own label-correction process (not a numbered acceptance criterion) is what NFR-FV03-016's "must score 1.0" bar exists to catch (§9), and FV03.7's two named limitations (`runtime.agent_traces` still has no writer, and pool sizing is a fixed constant rather than configurable — §9).

A follow-up code review, run after the first five specs were unit-tested, found that three pieces had been implemented and tested in isolation but never reached the running application: `_build_default_chatbi_application()` never passed the FV03.3 reranker or FV03.5 `vector_candidate_source` into `InMemoryKnowledgeStore`'s constructor; `handle_eval_run()` never computed or passed FV03.4's `retrieval_metrics` into `EvaluationScorer.score_suite()`; and `FileScopedRetriever`/`FileProcessingWorker` still embedded queries and uploaded-file chunks with the deterministic fallback instead of FV03.1's real configured `EmbeddingClient`. All ten findings from that review (these three plus seven correctness bugs — a missing `::vector` SQL cast, unclosed Postgres connections, a `normalize_scores()` degenerate-case regression, a `reranked_count` invariant break, and others) were fixed and covered by regression tests, which is what FV03.6 and FV03.7 (the embedding-reload fix, the real Golden Dataset, and durable observability storage for mining it further) grew out of.
