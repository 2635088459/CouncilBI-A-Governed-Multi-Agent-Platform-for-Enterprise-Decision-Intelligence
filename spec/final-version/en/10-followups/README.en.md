# Spec FV10.1–FV10.14: Follow-Up Specs Index

中文版：[../../zh-CN/10-followups/README.zh-CN.md](../../zh-CN/10-followups/README.zh-CN.md)

These twelve specs — FV10.1 through FV10.6, then FV10.9 through FV10.14 — turn most of the [10-followups system design set](../../../../system_design/final-version/en/10-followups/README.en.md) into testable requirements, following this project's SDD+TDD convention: every functional requirement (FR-) has at least one acceptance criterion (AC-) and at least one test case (TC-), and every test case traces back to a requirement. **Design docs 10.7 and 10.8 have no corresponding spec** — like FV10.5, both were implemented directly from their design documents during live-container bug reproduction, and no spec was written down for either; Spec FV10.9's own header records this explicitly rather than fabricating a link to a Spec FV10.8 that does not exist. Requirement IDs continue the parent [Spec FV-10](../10-user-file-upload-and-hybrid-analysis.spec.en.md) numbering (FR-FV10-037 through FR-FV10-091, spanning gaps left by 10.7/10.8's un-specced fixes); AC and TC numbering continues from that spec's highest existing IDs through AC-FV10-105 and TC-FV10-218.

Build order matches the dependency chain, not the numbering:

1. [Spec FV10.1: RAG Per-User Isolation](01-rag-per-user-isolation.spec.en.md) — build first; FV10.2 and FV10.3 both depend on its ownership model.
2. [Spec FV10.2: File Sharing Approval Workflow](02-file-sharing-approval-workflow.spec.en.md) — depends on FV10.1's `shared_visibility()` hook.
3. [Spec FV10.3: File Retention, Auto-Archival, and Re-Upload Dedup](03-file-retention-and-archival.spec.en.md) — depends on FV10.1's promotion-removal logic (reused for archival).
4. [Spec FV10.4: Multi-Turn Conversation Memory](04-multi-turn-conversation-memory.spec.en.md) — independent of the other three; can be built in parallel.
5. [Spec FV10.5: RAG-Only Routing and Knowledge Promotion Durability](05-rag-only-routing-and-promotion-durability.spec.en.md) — independent of FV10.1–FV10.4; found and fixed during Docker end-to-end verification of the other four, reuses FV10.1's `KnowledgePromotionService` unchanged.
6. [Spec FV10.6: Hybrid File Answering for Mixed Structured/Unstructured Selections](06-hybrid-file-answering-for-mixed-selections.spec.en.md) — depends on FV10.5's structured/unstructured file split; finally implements parent Spec FV-10's FR-FV10-023/FR-FV10-025, specified there but never built.

## Status

All twelve specs are fully decided with acceptance criteria and test cases and are implemented — including FV10.4's FR-FV10-055 (file attachments persist per-session, Option A) and FR-FV10-056 (follow-ups resolved via message history only, no rewriting step, Option B), both of which were confirmed after this index was first written. FV10.5 differs from FV10.1–FV10.4 in one respect: its two defects were discovered through live end-to-end testing, not design review, and its code fix (including a second bug — FR-FV10-062 — found only by writing an orchestrator-level test case) landed before its spec was written down; that spec documents and locks in behavior that was already implemented and verified. FV10.6 was written ahead of implementation, in the usual SDD+TDD order, then implemented and verified — including a real end-to-end test against a running Docker stack with a live LLM, not just the unit/integration test suite. Implementation surfaced that FR-FV10-067/068's evidence-labeling mechanism already existed in `ResultMerger` (it only needed its `uploaded_file_evidence` parameter populated, not new frontend code) — the source design doc's §6 had assumed new frontend rendering would be needed; the spec's §6.3 corrects this. FV10.9 followed FV10.5's spec-after-implementation order rather than FV10.6's spec-first one, for the same reason FV10.5 did — it, too, was found and fixed via live reproduction, not designed ahead of time; its own §10 records a design correction (a first-proposed corroboration check found backwards for the reported bug, before any code was written) that predates the spec itself.

FV10.10 was written ahead of implementation, in FV10.6's spec-first order, then implemented following this project's own TDD guidance verbatim: its test cases (TC-FV10-184 through TC-FV10-188) were written first, confirmed to fail against the unfiltered code for the expected reason, and then the filter was implemented. Running the *full* suite immediately afterward — not just the five new tests — regressed FV10.9's own test: the filter's first version had no guard against running on a pure-structured selection, silently undoing FV10.9's safety net for the exact request it exists to protect. FR-FV10-083 and TC-FV10-197 record the fix. This is the same class of correction FV10.9's own §10 (and, before it, FV10.8's month-name-token gap) represents, just caught at a different point in the process: FV10.9's correction happened before any code was written; FV10.10's happened after code and tests existed, by running the existing suite.

FV10.11 followed the same spec-first order and TDD discipline as FV10.10, but its own correction was caught earlier still: while writing TC-FV10-195's fixture data — before that test was ever run against real code, let alone before any live check — it surfaced that the motivating case's 6-value `month` column takes the `sample_values` branch (per AC-FV10-080) and gets truncated by `SAMPLE_SIZE` to 5 entries, not the `sample_range` branch AC-FV10-086's first draft had assumed would reveal the exact literal the test's question asks about. The test's fake LLM client was redesigned around detecting format revelation (a regex match for an ISO-date-shaped token) rather than the literal target value's presence, simulating a model that generalizes a format from examples — then confirmed against a real OpenAI-backed LLM, which did exactly that. See FV10.11's own §10 for the full account, and its source design's §4 for the live-verification result.

FV10.12 and FV10.13 were both found the same way: by reading the exact code path a single reported answer's response actually traversed, rather than a live LLM replay or a design review, since each root cause is structural (reproducible for any input matching its trigger condition) rather than a one-off model mistake. Both were written spec-first, per FV10.6/FV10.10/FV10.11's order rather than FV10.5/FV10.9's found-and-fixed-on-the-spot order, then implemented — their own §10s confirm every listed test case failed against the pre-implementation code for the expected reason before any production code was written, the SDD+TDD "red" step this project's convention requires. FV10.12 needed its own correction, caught the same way FV10.11's was — while building a test fixture, before that fixture was run against any code: measured against `InMemoryKnowledgeStore`'s real scoring behavior, its originally proposed `0.35` relevance floor excluded a genuinely relevant document a pre-existing test (`tests/test_chat_query_file_rag_analytics.py`) already asserted is returned, while admitting reconstructions of the originally reported bug's own two unrelated documents (which scored 0.3502 and 0.4011, both above 0.35). The floor was lowered to `0.15` to preserve the passing regression test, at the cost of no longer reliably excluding that reconstructed noise — see FV10.12's own §10 for the full account. FV10.13's implementation surfaced one contract its original §6 omitted: `status_code_for_envelope()` had no branch for the new `SQL_NOT_QUERYABLE` code and would have silently returned HTTP `200` for a response with a non-null `error` field; a `400` branch was added, matching the status this function already uses for `REQ_INVALID_ARGUMENT`. FV10.13's frontend acceptance criterion (AC-FV10-103) also could not be verified by an automated test — this project has no existing component-level test harness for `frontend/src/App.tsx` — and was instead verified by a clean `tsc --noEmit` compile plus direct code review; see FV10.13's own §10.

FV10.14 followed FV10.5's and FV10.9's after-the-fact order: a live re-test of the exact question FV10.12 was written to fix, run after FV10.12's code had already landed in the source tree, still reproduced the original bug. Two distinct causes, found in sequence: first, the running Docker containers were serving an image built before FV10.12's fix — a deployment gap (`Dockerfile.backend`/`Dockerfile.worker` copy source into the image at build time; a rebuild and restart were required, not a code change) — and second, once that was corrected, FV10.12's `zero_row_join_caveat` trigger condition looked for the literal substring `"join"` in the generated SQL, which a model asked to "compare ... and flag differences" is not obligated to produce (it reached for `EXCEPT` instead). FV10.14 replaced that literal-keyword check with one that inspects whether the query references both source views at all, and verified the fix against a rebuilt Docker deployment with a real `gpt-4o-mini`-backed LLM client — the exact reported question now returns the corrected join-mismatch caveat message; see FV10.14's own §10 and its source design's §4 for the full reproduction and verification transcript.

The full project test suite (1396 tests, excluding the pre-existing Postgres-credential tests, frontend-bundle assertion tests, static-analysis tests over unrelated pre-existing code, and a markdown-link-resolution test on an unrelated pre-existing file — all documented failures independent of FV10.12/FV10.13) passes after both specs' implementation.
