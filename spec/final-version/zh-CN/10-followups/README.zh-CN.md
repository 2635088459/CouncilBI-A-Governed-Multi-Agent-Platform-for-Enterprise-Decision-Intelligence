# Spec FV10.1–FV10.14：后续 Spec 索引

English: [../../en/10-followups/README.en.md](../../en/10-followups/README.en.md)

这十二份 Spec——FV10.1 到 FV10.6，再加上 FV10.9 到 FV10.14——把 [10-followups 系统设计文档集](../../../../system_design/final-version/zh-CN/10-followups/README.zh-CN.md) 里的大部分内容转化成了可测试的需求，遵循本项目的 SDD+TDD 惯例：每条功能需求（FR-）至少对应一条验收标准（AC-）和一条测试用例（TC-），每条测试用例都能追溯回一条需求。**设计文档 10.7 和 10.8 没有对应的 Spec**——跟 FV10.5 一样，这两篇都是在真实容器上做 bug 复现时直接从设计文档实现的，没有为它们单独写过 Spec；Spec FV10.9 自己开头就明确记录了这一点，而不是伪造一个指向根本不存在的 Spec FV10.8 的链接。需求编号延续父 [Spec FV-10](../10-user-file-upload-and-hybrid-analysis.spec.zh-CN.md) 的编号体系（FR-FV10-037 到 FR-FV10-091，中间跨过了 10.7/10.8 那两个没写 Spec 的修复留下的号段）；AC 和 TC 编号从该 Spec 现有最大编号继续，一路编到 AC-FV10-105 和 TC-FV10-218。

4. [Spec FV10.4：多轮对话记忆](04-multi-turn-conversation-memory.spec.zh-CN.md)——跟其余三份相互独立，可以并行开工。

## 现状

这十二份 Spec 现在全部都已经完全确定，带有完整的验收标准和测试用例，并且都已经实现——包括 FV10.4 的 FR-FV10-055（文件附件按会话延续，方案 A）和 FR-FV10-056（追问完全靠消息历史解析，不设改写步骤，方案 B），这两条是在本索引最初写完之后才拍板确认的。FV10.5 跟 FV10.1–FV10.4 有一点不同：它的两个缺陷是通过实际的端到端测试发现的，不是设计评审发现的，而且它的代码修复（包括第二个 bug——FR-FV10-062——是仅靠写一条编排器级测试用例才抓出来的）在它的 Spec 被写下来之前就已经落地并验证过了；那份 Spec 记录并锁定的是已经实现、已经验证过的行为。FV10.6 是按 SDD+TDD 通常的顺序、先写 Spec 再实现的，实现完之后也验证过了——不光是单元/集成测试套件，还对着真实跑起来的 Docker 服务、用真实 LLM 做了一次端到端验证。实现过程中发现 FR-FV10-067/068 的证据标注机制其实在 `ResultMerger` 里本来就有（只需要把它的 `uploaded_file_evidence` 参数填上，不需要写新的前端代码，不是最初设计文档里以为的那样）；这一点已经体现在现在这份 Spec 里，不是一份过时的初稿。FV10.9 走的是 FV10.5 那种"先实现、后补 Spec"的顺序，不是 FV10.6 那种"先写 Spec"的顺序，原因也一样——它同样是靠真实复现发现并修复的，不是提前设计出来的；它自己的第 10 节记录了一次设计修正（最初提议的交叉验证方案，拿报告里那个问题一验证，在任何代码写出来之前就发现是反的），这次修正比这份 Spec 本身还要早。

FV10.10 是按 FV10.6 那种"先写 Spec"的顺序写出来的，实现的时候也原原本本照着本项目自己的 TDD 指导来做：先写测试用例（TC-FV10-184 到 TC-FV10-188），确认它们针对未过滤的代码、因为预期的原因失败，然后才实现这道过滤。紧接着跑了一遍*全量*测试套件——不只是这五条新测试——就回归了 FV10.9 自己的测试：这道过滤最初的版本，没有针对"纯结构化选择"这种情况加任何门禁，悄悄撤销了 FV10.9 的安全网正是为了保护的那种请求。FR-FV10-083 和 TC-FV10-197 记录的就是这次修复。这跟 FV10.9 自己第 10 节（以及在它之前，FV10.8 那个月份名词元的缺口）记录的是同一种性质的修正，只是发生在整个流程里不同的时间点：FV10.9 的修正发生在任何代码写出来之前；FV10.10 的修正发生在代码和测试都已经写好之后，靠的是跑既有的测试套件。

FV10.11 跟 FV10.10 走的是同一套"先写 Spec"的顺序、同样严格遵循 TDD，但它自己的修正被抓到的时间点比 FV10.10 还要早：就在写 TC-FV10-195 的夹具数据时——那条测试还从来没有针对真实代码跑过，更别说做过任何实盘检查——就暴露出触发问题的那个场景里，`month` 列的 6 个取值走的是 `sample_values` 分支（按 AC-FV10-080），会被 `SAMPLE_SIZE` 截断成 5 条，不是 AC-FV10-086 最初草稿假设的那个会揭示出测试问题需要的确切字面量的 `sample_range` 分支。测试用的假 LLM client 因此被重新设计成检测"格式有没有被揭示"（正则匹配一个类 ISO 日期的词元），而不是检测目标字面量在不在——模拟的是一个能从样例里归纳出格式的模型——之后又拿真实的 OpenAI LLM 确认过，它确实就是这么做的。完整的经过见 FV10.11 自己的第 10 节，实盘验证的结果见它来源设计文档的第 4 节。

FV10.12 和 FV10.13 的发现方式一样：直接阅读某一次真实回答的响应实际走过的代码路径，而不是重放某一次具体的 LLM 调用,也不是设计评审;两个根因都是结构性的(只要输入满足各自的触发条件就能复现),不是模型偶然犯的一次错误。两者都按 FV10.6/FV10.10/FV10.11 的顺序先写 Spec，而不是 FV10.5/FV10.9 那种"当场发现、当场修复"的顺序,然后实现——各自的第 10 节都确认了:在写任何生产代码之前,列出的每一条测试用例针对实现之前的代码,确实因为预期的原因失败了,这是本项目约定要求的 SDD+TDD"红灯"步骤。FV10.12 自己也需要一次修正,被抓到的时间点跟 FV10.11 一样早——在构造测试数据的过程中,那份数据还没有拿去跑任何代码:对照 `InMemoryKnowledgeStore` 真实的评分行为实测,最初提议的 `0.35` 相关性下限,会排除掉一篇既有测试(`tests/test_chat_query_file_rag_analytics.py`)已经断言应该返回的、真正相关的文档,同时又放行了报告里那个 bug 本身那两篇不相关文档的复现版本(分数分别是 0.3502 和 0.4011,都高于 0.35)。这道下限被降到了 `0.15`,保住了既有回归测试通过,代价是不再能可靠地排除那类复现出来的噪音——完整经过见 FV10.12 自己的第 10 节。FV10.13 的实现过程暴露出原来第 6 节漏掉的一处契约:`status_code_for_envelope()` 对新增的 `SQL_NOT_QUERYABLE` 代码完全没有对应分支,原本会对一个 `error` 字段非空的响应悄悄返回 HTTP `200`;已经新增了一条 `400` 分支,跟这个函数已经在用的 `REQ_INVALID_ARGUMENT` 状态码保持一致。FV10.13 的前端验收标准(AC-FV10-103)也没能靠自动化测试验证——本项目目前没有针对 `frontend/src/App.tsx` 的组件级测试基础设施——改为靠一次干净通过的 `tsc --noEmit` 编译加直接代码审查来验证,详见 FV10.13 自己的第 10 节。

FV10.14 走的是 FV10.5、FV10.9 那种"先实现、后补文档"的顺序:拿触发 FV10.12 的那个原始问题重新做实盘复测,是在 FV10.12 的代码已经落进源码树之后进行的,结果依然复现了原始 bug。先后发现了两个不同的原因:第一，跑着的 Docker 容器还是 FV10.12 修复前构建的旧镜像——这是一个部署缺口(`Dockerfile.backend`/`Dockerfile.worker` 是在构建时把源码拷进镜像的，必须重新构建、重启才能生效，不是代码本身的问题)；第二，修正这一点之后，又发现 FV10.12 的 `zero_row_join_caveat` 触发条件是靠生成的 SQL 里有没有字面出现 `"join"` 这个词——而一个被要求"对比……并标出差异"的模型完全不需要一定写 `JOIN` 语法（这次它改用了 `EXCEPT`）。FV10.14 把这道字面关键词检查换成了"这条查询是不是真的同时引用了两个数据源视图"，并针对一个重新构建过的 Docker 部署、用真实的 `gpt-4o-mini` LLM client 验证过修复效果——报告里那个原始问题现在返回的是修正后的 join 不匹配提示消息；完整的复现和验证记录见 FV10.14 自己的第 10 节，以及它来源设计文档的第 4 节。

两份 Spec 实现完成之后,整个项目测试套件(1396 个测试,不含本项目自己的惯例早已记录为无关的、既有的 Postgres 凭据类测试、前端构建产物类断言测试、针对无关既有代码的静态分析测试,以及一个针对无关既有文件的 markdown 链接解析测试)全部通过。
