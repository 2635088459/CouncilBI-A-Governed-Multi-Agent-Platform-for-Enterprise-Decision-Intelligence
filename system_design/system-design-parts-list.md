# 系统设计清单

## 1. 文档目的

本文档基于主 README，列出本项目中所有需要单独进行系统设计的部分，作为后续架构设计、模块设计、接口设计、数据设计和评估设计的总清单。

项目定位是一个面向企业决策智能的多智能体 ChatBI 平台，因此设计范围不能只覆盖“聊天问答”，还需要覆盖数据治理、安全治理、可解释性、评估、可观测性和工程落地。

---

## 2. 设计范围总览

建议将系统设计拆成以下 10 个一级部分：

1. 产品与业务流程设计
2. 多智能体协同架构设计
3. NL2SQL 与语义层设计
4. SQL 安全与治理设计
5. 数据查询与分析能力设计
6. RAG 检索与证据解释设计
7. 前端交互与可视化设计
8. 后端服务与接口设计
9. 数据层与存储设计
10. 评估、审计、监控与运维设计

---

## 3. 需要设计的系统部分

## 3.1 产品与业务流程设计

这一部分定义系统对外提供什么能力，以及用户问题在系统中如何流转。

需要设计的子部分：

1. 用户角色设计
   Business User、Data Analyst、Engineering Team 的权限边界和使用方式。
2. 核心业务场景设计
   KPI 查询、对比分析、异常检测、趋势预测、原因解释、追问式分析。
3. 端到端流程设计
   从用户提问到最终回答的完整链路，包括路由、校验、执行、解释、验证、返回。
4. 会话与上下文设计
   多轮对话如何保留上下文，如何处理追问、改写问题、引用上一次结果。
5. 输出结果结构设计
   文本结论、表格结果、图表、异常标记、预测结果、证据引用、风险提示如何统一组织。

设计重点：

1. 明确不同问题类型对应的标准处理流程。
2. 明确最终回答的固定输出骨架，方便前后端和 Agent 协作。

---

## 3.2 多智能体协同架构设计

README 已经明确系统采用 Orchestrator + Specialized Agents 的模式，这部分必须单独设计。

需要设计的子部分：

1. Orchestrator Agent 设计
   负责意图识别、任务分类、任务拆解、路由、结果汇总。
2. SQL Agent 设计
   负责指标识别、SQL 生成、SQL 解释、调用 Guardrail、执行查询。
3. Visualization Agent 设计
   负责图表类型选择、图表配置生成、结果集降采样或聚合。
4. Analytics Agent 设计
   负责异常检测、预测、季节性分析、趋势解释。
5. RAG Agent 设计
   负责检索业务文档、抽取证据、形成原因解释候选。
6. Verifier Agent 设计
   负责校验 SQL 安全性、指标定义、结果一致性、解释可信度。
7. Agent 间通信协议设计
   输入输出 schema、状态传递、错误码、置信度字段。
8. Agent 调度策略设计
   串行、并行、条件分支、失败重试、超时中断、降级返回。

设计重点：

1. 每个 Agent 的职责边界必须清晰，避免功能重叠。
2. 需要定义统一的中间结果结构，否则后续实现会非常混乱。

---

## 3.3 NL2SQL 与语义层设计

这是项目最核心的基础能力之一，需要分别从“语义建模”和“SQL 生成”两个层面设计。

需要设计的子部分：

1. 业务语义层模型设计
   metric、dimension、time grain、filter、join path、业务别名。
2. 指标定义规范设计
   revenue、refund_rate、active_users 等核心指标的标准定义方式。
3. 语义配置文件设计
   `metrics.yaml` 或等价结构的 schema、版本管理、扩展规则。
4. 自然语言解析设计
   如何从问题中识别指标、维度、时间范围、比较对象、分析意图。
5. SQL 生成策略设计
   模板式、规则式、LLM 生成式、混合式的选型与约束。
6. SQL 解释生成设计
   生成给用户看的 SQL 逻辑说明，提升可解释性。
7. SQL 执行前校验入口设计
   在生成后进入 Guardrail 的调用时机和数据格式。

设计重点：

1. 语义层要先于 SQL 设计，否则指标会不稳定。
2. 必须定义“用户问题到语义对象”的映射规则。

---

## 3.4 SQL 安全与治理设计

这是企业级可用性的关键模块，README 中已经明确是重点亮点。

需要设计的子部分：

1. SQL 白名单与黑名单规则设计
   只允许 `SELECT`，禁止 `DROP`、`DELETE`、`UPDATE`、`INSERT`、`ALTER` 等语句。
2. SQL 语法与 AST 校验设计
   判断 SQL 是否只读、是否存在危险函数、是否越权访问。
3. 行数限制设计
   自动追加 limit 策略、分页策略、大结果集处理策略。
4. 查询超时设计
   超时阈值、取消机制、超时提示。
5. 表级和字段级权限设计
   哪些用户可查哪些表、哪些字段需要脱敏或禁止访问。
6. 审计日志设计
   记录用户问题、生成 SQL、执行状态、耗时、错误信息、命中规则。
7. 失败降级设计
   SQL 被拦截、执行失败、权限不足时的安全返回方式。

设计重点：

1. 设计要覆盖“防错”和“防攻击”两类风险。
2. 安全治理不应只停留在 prompt 层，必须有后端规则层。

---

## 3.5 数据查询与分析能力设计

这一部分负责结构化数据计算与高级分析能力落地。

需要设计的子部分：

1. 查询执行服务设计
   数据库连接、连接池、查询执行器、结果格式标准化。
2. 多维分析设计
   对比分析、分组聚合、趋势分析、Top N 分析。
3. 异常检测模块设计
   Bollinger Bands、rolling mean/std、SPC 规则的输入输出和策略选择。
4. 预测模块设计
   ARIMA、Prophet 的调用接口、训练窗口、结果置信区间。
5. 模型选择与回退策略设计
   不同数据量、数据周期下如何选择方法，失败时如何回退。
6. 分析结果表达设计
   如何把统计结果转换为可展示、可解释的业务语言。

设计重点：

1. 统计计算结果需要与业务指标定义保持一致。
2. 必须输出不确定性说明，不能把预测当作确定事实。

---

## 3.6 RAG 检索与证据解释设计

这一部分负责把结构化数据结果和非结构化业务上下文结合起来。

需要设计的子部分：

1. 文档源设计
   周报、发布说明、营销活动记录、工单、事故报告、财务报告、外部新闻。
2. 文档入库与切片设计
   文档清洗、chunk 策略、元数据结构、时间字段、来源字段。
3. 向量检索设计
   embedding、向量库选型、召回策略、过滤条件。
4. 混合检索设计
   关键词检索 + 向量检索的结合方式。
5. 证据排序与去重设计
   多文档命中时如何排序、去重、裁剪。
6. 证据引用设计
   最终回答如何引用证据、区分事实和推断。
7. RAG Faithfulness 约束设计
   防止编造因果关系，明确“不确定”和“可能原因”。

设计重点：

1. RAG 不是简单搜文档，而是要服务于“解释指标变化”。
2. 必须把证据引用格式设计清楚，方便审计和前端展示。

---

## 3.7 前端交互与可视化设计

README 已明确有前端页面与图表区域，因此前端不是简单聊天框，也需要单独系统设计。

需要设计的子部分：

1. ChatBI 会话页面设计
   输入区、消息流、追问入口、建议问题、状态提示。
2. 查询结果展示设计
   表格、指标摘要、SQL 说明、错误提示、空结果提示。
3. 图表展示设计
   时间序列图、柱状图、对比图、异常图、预测图的统一渲染协议。
4. 查询历史页面设计
   历史问题、SQL、时间、状态、可复现查看。
5. 数据集与指标管理页面设计
   指标定义浏览、数据集说明、权限显示。
6. 评估演示页面设计
   展示测试问题、期望结果、实际结果、评估分数。
7. 前端状态管理设计
   查询中、部分成功、失败、Agent 处理中间状态如何呈现。

设计重点：

1. 前端需要支持结构化结果，而不是只渲染文本。
2. 图表配置格式要与 Visualization Agent 输出保持一致。

---

## 3.8 后端服务与接口设计

这一部分负责把前端、Agent、数据库、向量库和评估能力连接起来。

需要设计的子部分：

1. API 网关或主后端设计
   用户请求接入、鉴权、路由、聚合返回。
2. AI 服务层设计
   Prompt 管理、模型调用、Agent 编排、结果缓存。
3. 查询接口设计
   提问接口、结果查询接口、历史记录接口。
4. 图表与分析接口设计
   图表 spec 返回、异常检测结果返回、预测结果返回。
5. RAG 检索接口设计
   检索请求、证据返回、来源信息返回。
6. 管理接口设计
   指标配置管理、评估任务管理、日志查询。
7. 错误处理与统一响应设计
   响应码、错误分类、用户可见提示、内部诊断信息。
8. 缓存设计
   Redis 缓存热点查询、会话上下文、短时结果复用。

设计重点：

1. 后端接口要围绕前端真实页面和 Agent 协作需要来定义。
2. 统一响应 schema 很关键，否则前端和 Agent 都会难以对接。

---

## 3.9 数据层与存储设计

README 给出了推荐表和存储组件，这一层需要完整建模。

需要设计的子部分：

1. 业务数据库 schema 设计
   `orders`、`products`、`customers`、`regions`、`refunds`、`marketing_campaigns`、`web_events`、`support_tickets`。
2. 核心指标口径与数据血缘设计
   指标从哪些表计算、如何 join、是否存在口径冲突。
3. 向量库设计
   文档向量、元数据过滤、索引更新。
4. 缓存层设计
   热点问题缓存、相似问题缓存、指标定义缓存。
5. 日志与审计存储设计
   query history、agent trace、安全拦截记录、评估记录。
6. 配置存储设计
   prompt、metrics config、权限规则、模型参数。

设计重点：

1. 要区分业务数据、知识数据、运行数据、治理数据四类存储。
2. 指标口径和数据血缘建议单独画图说明。

---

## 3.10 评估、审计、监控与运维设计

README 明确提出 evaluation、logging、observability，这部分必须纳入系统设计，而不是实现后补。

需要设计的子部分：

1. SQL Accuracy 评估设计
   表选择、字段选择、聚合函数、时间过滤、指标口径正确性。
2. SQL Safety 评估设计
   危险语句拦截、敏感字段访问、只读执行保证。
3. Agent Routing 评估设计
   不同问题类型是否选择了正确 Agent 组合。
4. RAG Faithfulness 评估设计
   是否命中正确文档、是否有无证据结论、是否清楚表达不确定性。
5. 延迟指标设计
   SQL latency、RAG latency、forecast latency、full workflow latency。
6. 可观测性设计
   trace id、agent step trace、错误告警、性能监控。
7. 查询历史与审计设计
   历史问题回放、SQL 回放、证据回放、结果复盘。
8. 部署与环境设计
   `.env`、`docker-compose`、本地开发环境、测试环境。

设计重点：

1. 评估标准应在 MVP 阶段就确定，否则系统质量无法证明。
2. 审计和可观测性是企业级项目的重要区分项。

## 4. 建议优先级

如果后续要分文档逐步写，建议优先顺序如下：

1. 总体架构设计
2. 多智能体协同设计
3. NL2SQL 与语义层设计
4. SQL 安全与治理设计
5. 数据层设计
6. 后端接口设计
7. 前端交互与可视化设计
8. RAG 设计
9. 分析与预测设计
10. 评估与可观测性设计

原因：

1. 前四项决定项目是否能成立。
2. 数据层和接口层决定能否实现。
3. RAG、分析、评估决定项目是否具备亮点和可信度。

## 6. 当前结论

基于主 README，本项目不是只需要一个“聊天系统设计”，而是至少需要覆盖以下关键系统：

1. 会话与业务流程系统
2. 多智能体编排系统
3. 语义层与 NL2SQL 系统
4. SQL 安全治理系统
5. 数据查询与分析系统
6. RAG 检索与证据解释系统
7. 前端展示与可视化系统
8. 后端服务与接口系统
9. 数据与存储系统
10. 评估、审计、监控与运维系统

这 10 个部分共同构成完整的企业级 ChatBI 决策智能平台设计范围。
