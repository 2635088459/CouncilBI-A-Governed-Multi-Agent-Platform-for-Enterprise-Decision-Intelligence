# 4.5 Production Vector Search with pgvector

## 1. Problem Solved

Everything [4.1](01-unifying-the-vector-and-hybrid-retrieval-paths.en.md)–[4.4](04-golden-dataset-hit-rate-and-mrr-evaluation.en.md) build runs on `InMemoryKnowledgeStore`'s process-local dictionaries: every embedding lives only in RAM, a restart loses the entire index, there is no approximate-nearest-neighbor (ANN) index (search is a linear scan over every stored vector), and nothing is shared across multiple backend replicas. This document replaces the storage and vector-search layer with pgvector on the platform's existing Postgres instance, while deliberately leaving the BM25 scoring ([4.2](02-bm25-keyword-scoring.en.md)), cross-encoder rerank ([4.3](03-cross-encoder-reranking.en.md)), and evaluation harness ([4.4](04-golden-dataset-hit-rate-and-mrr-evaluation.en.md)) untouched — this phase only changes *where vectors live and how the nearest ones are found*, not how relevance is scored once they're found.

**Correction to this document's first draft:** an earlier version of this design targeted `rag.documents`/`rag.chunks`/`rag.embedding_metadata` (`rag_postgres_rows.py`) and the `VectorStore` protocol (`embedding_vector_rag.py`). Those belong to the separate vector-only evidence pipeline (`EmbeddingVectorRagService`/`InMemoryVectorRagRetriever`) that [4.1](01-unifying-the-vector-and-hybrid-retrieval-paths.en.md) deliberately retired from the orchestrator's live chat-query path in favor of `InMemoryKnowledgeStore`'s hybrid path. A "production vector search" phase must therefore target `InMemoryKnowledgeStore`'s own backing tables — `knowledge.documents`/`knowledge.doc_chunks`/`knowledge.doc_embeddings` (`migrations.py:372-410`) — not the retired pipeline's schema. §2–§3 below are corrected accordingly.

## 2. What Already Exists

- `knowledge.documents` / `knowledge.doc_chunks` / `knowledge.doc_embeddings` (`migrations.py:372-410`, `KNOWLEDGE_RAG_TABLES_SQL`) are the real Postgres tables `_load_knowledge_store_from_db()` (`api/http.py`) reads at startup to populate the live `InMemoryKnowledgeStore` — the store `RagAgentRunner` actually queries. `knowledge.doc_embeddings` stores only `embedding_model`, `embedding_dimensions`, and a `vector_ref TEXT` — a text reference, never the vector itself. There is no `vector`-typed column and no `pgvector` extension anywhere in this schema today.
- The string `"pgvector://..."` in `migrations.py:509,529` (`vector_ref` sample values) and `files/promotion.py:224`'s counterpart is a placeholder/example value, not a real client integration — there is no pgvector client library dependency in the project today.
- `InMemoryKnowledgeStore.list_chunk_records()` (`knowledge.py:218-255`) is the only place today's permission model — `owner_user_id`, `allowed_roles`, `doc_type`/`doc_types`, `tags`, and the `shared_visibility_resolver` hook (Spec FV10.1/FV10.2) — is actually enforced, entirely in Python, over every chunk in memory. None of it is expressed as SQL today.
- Real embeddings are already generated by `OpenAIEmbeddingClient` (`embedding_vector_config.py:19-63`, 1536 dimensions for `text-embedding-3-small`) once [4.1](01-unifying-the-vector-and-hybrid-retrieval-paths.en.md) wires it into `InMemoryKnowledgeStore.embed_text()` — this phase consumes that output, it does not need to generate embeddings itself.

## 3. Design

### 3.1 Schema migration

Add a real vector column and an index to `knowledge.doc_embeddings`, following this project's existing migration convention (`migrations.py`):

```sql
CREATE EXTENSION IF NOT EXISTS vector;

ALTER TABLE knowledge.doc_embeddings
    ADD COLUMN embedding vector(1536);

CREATE INDEX IF NOT EXISTS knowledge_doc_embeddings_hnsw_idx
    ON knowledge.doc_embeddings
    USING hnsw (embedding vector_cosine_ops);
```

`embedding` is nullable at first (existing rows have no vector yet — see §3.4). HNSW is chosen over IVFFlat: this project's corpus is small enough that HNSW's build cost is not a concern, and HNSW gives better recall at a given query latency without needing an upfront `lists` parameter tuned to corpus size the way IVFFlat does. The column lives on `knowledge.doc_embeddings` rather than `knowledge.doc_chunks` because that table already carries one row per `(chunk_id, embedding_model)` — the natural granularity for "this specific embedding" — rather than one row per chunk, which matters if the platform ever embeds the same chunk with two different models side by side (e.g. during a model migration).

### 3.2 `PostgresKnowledgeVectorSource`

New module, e.g. `knowledge_postgres_vector_source.py`. This is **not** an implementation of the existing `VectorStore` protocol (`embedding_vector_rag.py`) — that protocol's `search()` returns `EvidenceChunk`s shaped for the retired vector-only pipeline, and its `org_id`/`permission_tags` filter model doesn't match `InMemoryKnowledgeStore`'s actual `owner_user_id`/`allowed_roles`/`shared_visibility_resolver` permission model. A new, narrower protocol instead:

```python
class VectorCandidateSource(Protocol):
    def top_chunk_ids(
        self,
        *,
        query_vector: tuple[float, ...],
        requesting_user_id: str,
        user_role: str | None,
        doc_type: str | None,
        doc_types: tuple[str, ...],
        limit: int,
    ) -> tuple[tuple[str, float], ...]:  # (chunk_id, cosine_distance) pairs
        ...


class PostgresKnowledgeVectorSource:
    def __init__(self, connection_factory: Callable[[], Connection]) -> None:
        self._connection_factory = connection_factory

    def top_chunk_ids(self, *, query_vector, requesting_user_id, user_role, doc_type, doc_types, limit):
        # SELECT c.chunk_id, e.embedding <=> %(query_vector)s AS distance
        # FROM knowledge.doc_embeddings e
        # JOIN knowledge.doc_chunks c ON c.chunk_id = e.chunk_id
        # JOIN knowledge.documents d ON d.source_id = c.source_id
        # WHERE e.embedding IS NOT NULL
        #   AND (d.owner_user_id IS NULL OR d.owner_user_id = %(requesting_user_id)s)
        #   AND (%(user_role)s IS NULL OR d.allowed_roles = '{}' OR %(user_role)s = ANY(d.allowed_roles))
        #   AND (%(doc_type)s IS NULL OR d.doc_type = %(doc_type)s)
        #   AND (%(doc_types)s = '{}' OR d.doc_type = ANY(%(doc_types)s))
        # ORDER BY e.embedding <=> %(query_vector)s
        # LIMIT %(limit)s
        ...
```

The `owner_user_id`/`allowed_roles`/`doc_type` filters run **inside the SQL `WHERE` clause**, not as a post-filter in Python — this is a deliberate, non-negotiable design choice, not a style preference: [10.1 RAG Per-User Isolation](../10-followups/01-rag-per-user-isolation.en.md) documents a real, previously-shipped cross-tenant data leak in this platform's knowledge base caused by exactly this class of mistake (filtering applied after retrieval instead of scoping the query itself).

**Known gap, carried forward explicitly rather than silently dropped:** the `shared_visibility_resolver` hook (Spec FV10.2's file-sharing grants) is a Python callback with no SQL representation today — `top_chunk_ids()` above does not grant visibility to a shared-but-not-owned document. This phase's acceptance criteria (§3.5) only cover the owner/role/doc_type filters that *are* SQL-expressible; extending Spec FV10.2's share grants into a queryable table (so `PostgresKnowledgeVectorSource` can join against them) is out of this phase's scope and should be a Spec FV10.2 follow-up, not silently absorbed here.

### 3.3 Wiring into the unified retrieval path

[4.1](01-unifying-the-vector-and-hybrid-retrieval-paths.en.md) made `InMemoryKnowledgeStore`'s hybrid path (BM25 + vector + source-weight fusion, then [4.3](03-cross-encoder-reranking.en.md)'s rerank) the only retrieval mechanism reachable from a live chat query. This phase does not reintroduce a second path — it makes the *vector-candidate-generation step inside that one path* pluggable, while every permission filter `list_chunk_records()` already enforces in Python (§2) continues to run exactly as it does today, on whichever candidate set comes back:

1. `InMemoryKnowledgeStore` gains an optional `vector_candidate_source: VectorCandidateSource | None` constructor parameter. When set, `retrieve()` calls it to get the top-N `(chunk_id, distance)` pairs by vector similarity for the current query's `requesting_user_id`/`user_role`/`doc_type`/`doc_types`, then intersects that chunk-id set with `list_chunk_records()`'s existing, unchanged Python-side filtering (§3.2's known gap means this intersection is still required — the Postgres source is a candidate-narrowing prefilter, not a replacement authority for permissions).
2. When `vector_candidate_source` is `None` (today's behavior, and every existing test), `retrieve()` is unchanged — the in-memory linear cosine scan runs exactly as it does now.
3. `_rank_records()`'s BM25 term ([4.2](02-bm25-keyword-scoring.en.md)) and the fusion formula are unaffected either way — they already operate on whatever candidate set `list_chunk_records()`/the intersection above produces.

### 3.4 Backfill migration

A one-time script, not part of the request-serving code path: for every chunk currently indexed only through the in-memory path (i.e., every `knowledge.doc_embeddings` row with `embedding IS NULL`), call the real `EmbeddingClient` from [4.1](01-unifying-the-vector-and-hybrid-retrieval-paths.en.md) via `InMemoryKnowledgeStore.embed_text()` and `UPDATE` the row with the resulting vector. Batched to respect the embedding provider's rate limits (`OpenAIEmbeddingClient` already reports `token_count`/`estimated_cost` per call, which the backfill script logs for cost visibility). This script is the same shape as any other one-time repair/backfill job this project already runs via `migrate.py`/`migrations.py`.

### 3.5 Owner-isolation verification

Because [10.1](../10-followups/01-rag-per-user-isolation.en.md) documents a real prior incident of exactly this failure mode, this phase's acceptance criteria explicitly include a cross-owner test: seed two users' owned documents with overlapping content, and assert that a `PostgresKnowledgeVectorSource.top_chunk_ids()` call scoped to user A's `requesting_user_id` never returns a chunk belonging to user B's privately-owned document, verified against the actual SQL executed (the `WHERE d.owner_user_id ...` predicate is present), not by only checking the returned result set — a query that filters in Python after fetching everything would also pass a result-set-only assertion. §3.2's known gap (shared-visibility) means this test intentionally does **not** claim full parity with `list_chunk_records()`'s complete permission model — only that the owner/role/doc_type filters that are implemented are correctly scoped.

## 4. Effort Estimate

Roughly **4–6 person-days** (revised up from the first draft's 3.5–5, since the corrected target requires reconciling with `InMemoryKnowledgeStore`'s Python-side permission model rather than reusing an existing `org_id`-based protocol verbatim):

| Task | Estimate |
|---|---|
| Migration: `pgvector` extension, column, HNSW index on `knowledge.doc_embeddings` | 0.5 day |
| `PostgresKnowledgeVectorSource` implementation + conformance tests | 1.5–2 days |
| Making the vector-candidate-generation step pluggable inside `InMemoryKnowledgeStore.retrieve()`, including the candidate-set intersection with existing Python-side filtering | 1–1.5 days |
| Backfill script (re-embed and populate existing chunks via `embed_text()`) | 0.5–1 day |
| Owner-isolation test (§3.5) and general regression pass | 0.5–1 day |
