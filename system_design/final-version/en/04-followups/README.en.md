# 4 Follow-Up Designs: Real Retrieval Quality for the Hybrid Knowledge Base

中文版：[../../zh-CN/04-followups/README.zh-CN.md](../../zh-CN/04-followups/README.zh-CN.md)

These five documents extend [4 Embedding, Vector Search, and RAG](../04-embedding-vector-rag.en.md). They came out of an honest, code-level audit of what this platform's retrieval pipeline actually does versus what a hybrid-search RAG system is often described as doing (BM25 + vector fusion, cross-encoder reranking, real embeddings, an automated Hit Rate/MRR evaluation harness, and a production vector database). The audit found the architecture's *shape* already matches — a hybrid scoring formula and a documented four-stage pipeline already exist — but three of its four stages are placeholders: "vector" search runs on a deterministic hash-bucket pseudo-embedding rather than a real model on one live code path (and on real embeddings but with zero keyword scoring on the other, since two disjoint retrieval mechanisms exist side by side), "keyword" scoring is a plain token-overlap ratio rather than BM25, and "rerank" re-sorts by a score already computed one step earlier rather than running a second model pass. Evaluation, meanwhile, measures answer-level quality and latency only — there is no ground truth for "did retrieval find the right chunk" at all. Storage, finally, is entirely process-local — every embedding lives only in RAM, with no ANN index and nothing durable across a restart.

Read them in this order — each is a prerequisite for measuring the next accurately:

1. [4.1 Unifying the Vector-Only and Hybrid Retrieval Paths, and Wiring in Real Embeddings](01-unifying-the-vector-and-hybrid-retrieval-paths.en.md) — closes the gap where `RagAgentRunner` silently picks between a real-embeddings-but-no-keywords path and a hybrid-but-fake-embeddings path depending on which is wired in; makes the hybrid path the only one reachable from a live chat query, with a real embedding client behind it.
2. [4.2 Replacing Jaccard Keyword Overlap with Real BM25 Scoring](02-bm25-keyword-scoring.en.md) — replaces the query-token-coverage ratio currently doing the "keyword" half of hybrid scoring with actual BM25, computed per-request over the already permission-filtered candidate set, and fixes a silent Chinese-text tokenization gap along the way.
3. [4.3 Adding a Real Cross-Encoder Rerank Stage](03-cross-encoder-reranking.en.md) — builds the rerank stage the retrieval pipeline's own docstring already claims to have but doesn't: a second-pass cross-encoder re-score of the narrowed top-2K candidates, with a fallback to the pre-rerank ordering if the model is unavailable.
4. [4.4 A Golden Dataset and Automated Hit Rate / MRR Evaluation for Retrieval](04-golden-dataset-hit-rate-and-mrr-evaluation.en.md) — adds retrieval-specific ground truth (`expected_chunk_ids`) and metrics (Hit Rate@K, MRR) to the existing evaluation system as observability-only metrics, deferring a release-gate threshold until a real baseline exists; also the phase whose cost is dominated by manual dataset labeling, not code.
5. [4.5 Production Vector Search with pgvector](05-pgvector-production-vector-search.en.md) — replaces `InMemoryKnowledgeStore`'s in-memory vector store with pgvector on `knowledge.doc_embeddings` (the platform's existing Postgres instance): a schema migration, a `PostgresKnowledgeVectorSource` implementing a new `VectorCandidateSource` protocol, SQL-level owner/role scoping (closing the same class of leak [10.1](../10-followups/01-rag-per-user-isolation.en.md) already found once), a backfill migration, and an owner-isolation test as an explicit acceptance criterion.

## Status

Four of the five (4.1–4.4) are implemented (see this project's source tree and test suite). [4.5](05-pgvector-production-vector-search.en.md) is a proposed design, not yet implemented — building it is the current next step. They were written after a request to evaluate what it would take to close the gap between this project's actual retrieval implementation and a hybrid-search RAG system described in an unrelated example (a slide describing BM25 + vector fusion, a reranker, a Golden-Dataset-based Hit Rate/MRR evaluation pipeline, and named infrastructure like ElasticSearch/Redis). The audit that produced these five documents also surfaced, and corrected, an initial assumption: embeddings in this codebase are not simply "all mocked" — a real `OpenAIEmbeddingClient` (`embedding_vector_config.py:19-63`) already exists and is wired into one of the two retrieval paths [4.1](01-unifying-the-vector-and-hybrid-retrieval-paths.en.md) describes; the actual defect is that it is wired into the path with no keyword scoring, not that real embeddings are entirely absent from the codebase. [4.5](05-pgvector-production-vector-search.en.md) was initially scoped as an optional, deferred document, then revised into a fully-specified design at the same commitment level as 4.1–4.4 — but its first fully-specified draft targeted the wrong schema (`rag.embedding_metadata`, belonging to the vector-only pipeline 4.1 retires) and the wrong protocol (`VectorStore`, whose `org_id`/`permission_tags` model doesn't match `InMemoryKnowledgeStore`'s actual `owner_user_id`/`allowed_roles` model). §1/§2/§3 of 4.5 record and correct that mistake, once implementation of 4.1–4.4 made the actual target unambiguous.
