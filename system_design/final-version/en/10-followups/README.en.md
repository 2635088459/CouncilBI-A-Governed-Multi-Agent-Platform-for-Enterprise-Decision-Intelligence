# 10 Follow-Up Designs: RAG Isolation, Sharing, Retention, Conversation Memory, Routing & Promotion Durability, Hybrid File Answering, Cross-Turn SQL Contamination, File-Branch Relevance Gate

中文版：[../../zh-CN/10-followups/README.zh-CN.md](../../zh-CN/10-followups/README.zh-CN.md)

These fourteen documents extend [10 User File Upload and Hybrid Data Analysis](../10-user-file-upload-and-hybrid-analysis.en.md). The first four came out of post-implementation review: a real multi-tenant data-leak found in the RAG knowledge base, a corrected sharing/governance model, a retention model that matches "working set, not storage," and a conversation-memory design for follow-up questions. The fifth came out of Docker-based end-to-end verification of those four, which surfaced two further defects. The sixth is a forward-looking design for a gap 10.5 deliberately left unresolved. The seventh through eleventh, like the fifth, came out of live-container reproduction of user-reported bugs or a real regression/discrepancy the project's own test-writing process caught mid-implementation: the seventh found 10.4's conversation-history injection letting one turn's value formats leak into another turn's SQL generation; the eighth found that attaching any file forced every question through the file-only branch regardless of relevance; the ninth closed a specific hole the eighth's own gate left open, after an initially-proposed fix for it was checked against the reported bug and found backwards; the tenth closed a second hole the eighth's gate left open, and was itself corrected mid-implementation after its own first version regressed the ninth's test; the eleventh closed the third and last gap, and its own acceptance criteria needed correcting after writing its end-to-end test surfaced that the motivating case's own data didn't take the branch the design had assumed. The twelfth and thirteenth came from a single live analyst testing session against the running system, not a bug-report ticket: one answer's screenshots showed evidence rendered with no regard to relevance and a zero-row join result narrated as a confirmed "no variance" conclusion (twelfth), and a read-only explanatory question blocked with a guardrail message that misdescribed the block as a data-modification attempt (thirteenth); both were written spec-first and implemented. The fourteenth closed a residual gap in the twelfth: a live re-test of the exact reported comparison question, after the twelfth's fix had already landed, still reproduced the original bug — first because the running Docker containers were serving a stale pre-fix image, and once that was rebuilt, because the twelfth's join-detection heuristic missed a comparison query written with `EXCEPT` instead of literal `JOIN` syntax.

Read them in this order — each one assumes the concepts introduced before it:

1. [10.1 RAG Per-User Isolation](01-rag-per-user-isolation.en.md) — fixes a confirmed cross-tenant data leak in the knowledge base; introduces the baseline-knowledge vs. personal-knowledge split.
2. [10.2 File Sharing Approval Workflow](02-file-sharing-approval-workflow.en.md) — replaces admin-initiated promotion with analyst-requested, admin-approved sharing to same-role colleagues; widens RAG visibility from 10.1 as one consequence of approval.
3. [10.3 File Retention, Auto-Archival, and Re-Upload Dedup](03-file-retention-and-archival.en.md) — shortens retention windows, replaces destructive expiry with a reversible-by-re-upload archive, and ties archival to 10.1's RAG visibility.
4. [10.4 Multi-Turn Conversation Memory](04-multi-turn-conversation-memory.en.md) — session-scoped conversational context for SQL generation, RAG retrieval, and answer synthesis; file attachments persist across turns within a session, and follow-ups are resolved via message history with no separate rewriting step.
5. [10.5 RAG-Only Routing and Knowledge Promotion Durability](05-rag-only-routing-and-promotion-durability.en.md) — fixes document-only questions being wrongly gated behind a mandatory SQL step, and a knowledge-promotion path that could silently create a permanently-empty, unsearchable document.
6. [10.6 Hybrid File Answering for Mixed Structured/Unstructured Selections](06-hybrid-file-answering-for-mixed-selections.en.md) — request-scoped RAG retrieval over a user's own attached unstructured files, merged with structured-file SQL results into one synthesized answer, closing a gap 10.5 intentionally left as "don't crash" rather than "answer correctly."
7. [10.7 Cross-Turn Value-Format Contamination in File/Federated SQL Generation](07-cross-turn-value-format-contamination-in-file-sql-generation.en.md) — a prior turn's value formats (e.g. English month names from an unrelated business-table answer) could leak into a file query's generated `WHERE` clause, producing valid-but-empty SQL instead of an error; fixed with an explicit prompt instruction plus a narrower, file-branch-specific conversation-history window.
8. [10.8 A Question-Relevance Gate Before Routing to the File Branch](08-question-relevance-gate-before-file-branch-routing.en.md) — a file attached (possibly left over from an earlier turn) forced every question through FileDataAgent/FederatedQueryAgent regardless of relevance, producing a confidently-wrong answer or a bare SQL error instead of ever reaching the main orchestrator's real business tables; fixed with a no-LLM-call token-overlap relevance predicate, deliberately biased toward keeping genuine follow-ups in the file branch.
9. [10.9 A Data-Domain-Signal Safety Net for the Relevance Gate](09-data-domain-signal-safety-net-for-the-relevance-gate.en.md) — 10.8's token-overlap gate alone could misroute a genuinely file-relevant question phrased with a business synonym its schema doesn't literally contain; fixed by corroborating a "not relevant" verdict against `QuestionClassifier`'s existing business-data-keyword signal — after an initially-proposed corroboration check was found, on inspection, to be backwards for the reported bug's own question.
10. [10.10 Per-File Relevance Filtering for Mixed Structured/Unstructured Selections](10-per-file-relevance-filtering-in-mixed-selections.en.md) — extends 10.8's per-file relevance predicate to filter `structured_ids` inside a mixed selection, not just gate the request as a whole, closing the residual case where an irrelevant structured file still reached `FileDataAgent` alongside a relevant unstructured one; the filter deliberately does not run at all when no unstructured file is attached, after its first, unconditional version regressed 10.9's own safety net.
11. [10.11 Value-Sample-Aware Schema Context for File SQL Generation](11-value-sample-aware-schema-context.en.md) — a sibling of 10.7's failure mode found during 10.8/10.9's own live verification: a natural-language date reference typed directly into the current question (not carried over from history) can still be translated to a literal that doesn't match a file's real stored format, because the SQL-generation schema context included a column's name and type but never a sample of its actual values; fixed by computing a value sample once at file-upload time and rendering it into the SQL-generation prompt.
12. [10.12 Evidence Relevance Gating and Join-Mismatch Caveats for Hybrid File/Warehouse Comparison Answers](12-evidence-relevance-and-join-mismatch-caveats.en.md) — a single-word RAG-keyword false positive ("internal") pulled two unrelated documents into a file-comparison answer's "Sources" list with no relevance floor to stop them, and a `FederatedQueryAgent` join that matched zero rows because of a join-key mismatch was narrated as a confirmed "no variance" finding, indistinguishable in code from a real one; fixed with a relevance-score floor at the point evidence is rendered, plus a `zero_row_join_caveat` signal fed into answer synthesis when a `JOIN`-bearing query empties out despite non-empty sources — the floor's value had to be corrected mid-implementation (see 10.12's own §9) after it was measured to exclude a genuinely relevant document a pre-existing test already covered.
13. [10.13 Guardrail Deny-Reason Preservation for Non-SELECT LLM Output](13-guardrail-deny-reason-preservation.en.md) — a real DML/DDL keyword match and "the model just didn't produce SQL" were conflated into one `SqlValidationViolationCode`, then collapsed twice more on the way to the frontend, so a read-only "explain how you calculated X" question — asked about a metric with no matching table — was blocked with a message claiming a data-modification attempt; fixed with a new violation code, `ErrorCode`, and `ApiErrorCode` carrying the distinction through to a frontend message that describes what actually happened.
14. [10.14 Comparison-Query Detection for the Zero-Row Join Caveat, Beyond Literal JOIN Syntax](14-comparison-query-detection-beyond-literal-join.en.md) — closes a residual gap in 10.12: its `zero_row_join_caveat` only fired for SQL containing the literal word "join," but a model asked to "compare and flag differences" just as readily writes `EXCEPT` or `NOT EXISTS`, which evaded the check entirely and let the original "no differences" false conclusion recur; fixed by checking whether the query references both source views at all, regardless of which SQL construct it uses.

## Status

All fourteen are implemented and verified — 10.12 and 10.13 were written spec-first, per the usual SDD+TDD order, then implemented (see their own specs' §10/§9 for corrections found along the way). The two items originally left open in 10.4 (file-attachment stickiness, follow-up resolution strategy) have since been decided: file attachments persist per-session (Option A) and follow-ups are resolved purely via message history, with no explicit rewriting step (Option B). 10.5's two fixes were found and fixed on the spot during local Docker end-to-end verification of 10.1–10.4, not designed ahead of implementation. 10.6 was written as a forward-looking design first (per this project's usual SDD+TDD order), then turned into [Spec FV10.6](../../../../spec/final-version/en/10-followups/06-hybrid-file-answering-for-mixed-selections.spec.en.md) and implemented; that spec is the authoritative source for its exact requirement wording, which was refined twice during implementation (see 10.6's own §9). 10.7, 10.8, and 10.9, like 10.5, were found and fixed via live reproduction against a running Docker stack with a real LLM provider, not designed ahead of time. 10.7 documents two adjacent gaps deliberately left for a future followup (see 10.7's own §6). 10.8's own relevance predicate was itself revised mid-implementation after the project's test suite caught a regression its first version introduced (see 10.8's own §5) — its own §6 documents three further gaps left open. 10.9 closed the first of those three, after its own first-proposed design was checked against the reported bug's actual question and found to route the wrong way for it (see 10.9's own §3) — a correction caught before any code was written, one step earlier than 10.8's test-suite-caught regression. 10.10 closed the second, written and implemented in the usual SDD+TDD order (Spec FV10.10 first, then a red-then-green implementation) — but its own first, unconditional version of the filter regressed 10.9's test the same way 10.8's month-name gap was caught: by running the full suite, not by checking against a single reported case ahead of time (see 10.10's own §4). 10.11 closed the third and last gap, written and implemented in the same order — but needed its own correction at an earlier point in the process than either 10.9's or 10.10's: while writing its end-to-end test's fixture data, before that test was ever run, it surfaced that the motivating case's own 6-value column takes the `sample_values` branch and gets truncated by `SAMPLE_SIZE`, not the `sample_range` branch the design had assumed — the test's fake LLM client was redesigned around format-revelation rather than literal-value-presence as a result, then confirmed sound against a real LLM (see 10.11's own §4). 10.12 and 10.13 were both found by reading the exact code path a single reported answer's response traversed, not a live LLM replay, and both were written spec-first per FV10.6's order; 10.12 needed a correction of its own, caught while building its relevance-floor test's first fixture — measured against `InMemoryKnowledgeStore`'s real scoring behavior, its originally proposed `0.35` floor excluded a genuinely relevant document a pre-existing test already covered while admitting reconstructions of the originally reported bug's own unrelated documents, so the floor was lowered to `0.15` to preserve the passing test at the cost of no longer reliably excluding that noise (see 10.12's own §9).

10.14 followed 10.5's and 10.9's after-the-fact order, not FV10.6's spec-first one — its own defect was found the same way 10.5's and 10.9's were, via live reproduction, not designed ahead of time. A live re-test of the exact question that motivated 10.12, after 10.12's fix had already landed in the source tree, still reproduced the original bug — first because the running Docker containers were serving an image built before the fix (a deployment gap, not a code gap: `Dockerfile.backend`/`Dockerfile.worker` copy source into the image at build time, so a rebuild and restart were required), and after that was corrected, because 10.12's `zero_row_join_caveat` gated its trigger on the literal substring `"join"` appearing in the generated SQL — a model asked to "compare ... and flag differences" is not obligated to write `JOIN` syntax at all, and reached for `EXCEPT` instead, evading the check entirely. 10.14 replaced that literal-keyword gate with a check for whether the query references both source views at all, verified against a rebuilt Docker deployment with a real `gpt-4o-mini`-backed LLM client, which returned the corrected join-mismatch caveat message instead of the original false "no differences" conclusion (see 10.14's own §4).
