# 05 数据平台、迁移与大规模测试数据

## 1. 为什么要做数据平台和 seed

工业项目不能只靠几条手写数据演示。我们需要大量、可重复、可解释的数据来验证：

1. SQL 是否正确。
2. 分析预测是否稳定。
3. RAG 是否能检索到证据。
4. 权限隔离是否生效。
5. 系统在大数据量下是否还能响应。

一句话：没有数据，很多架构能力都只是纸上谈兵。

## 2. 数据分类

最终项目至少需要四类数据：

1. 应用数据：用户、组织、角色、会话、查询历史。
2. 业务数据：订单、客户、产品、地区、收入、退款等。
3. 知识数据：文档、chunk、embedding、citation。
4. 运行数据：trace、metrics、logs、eval、audit。

## 3. 数据库建议

### 3.1 PostgreSQL

用于：

1. 用户和权限。
2. 业务演示数据。
3. 查询历史。
4. 审计日志。
5. 评估结果。

### 3.2 Redis

用于：

1. 缓存。
2. 限流计数。
3. 短期任务状态。
4. session 或 token blacklist。

### 3.3 pgvector

用于：

1. 文档 chunk embedding。
2. semantic memory。
3. RAG 检索。

## 4. Migration 策略

数据库结构不能靠手工创建。需要 migration。

推荐要求：

1. 每次 schema 变化都有 migration 文件。
2. migration 可在本地、CI、云端一致运行。
3. migration 不和 seed 混在一起。
4. 生产 migration 要能回滚或至少有备份策略。

## 5. Seed 数据设计

Seed 数据分三档：

### 5.1 Small

用于单元测试和快速 demo。

规模：

1. 2 个组织。
2. 5 到 10 个用户。
3. 几百条业务记录。
4. 几十个文档 chunk。

### 5.2 Medium

用于本地集成测试。

规模：

1. 5 到 10 个组织。
2. 几十个用户。
3. 十万级业务记录。
4. 几千个文档 chunk。

### 5.3 Large

用于压测和云端验证。

规模：

1. 多组织。
2. 百万级业务记录。
3. 十万级文档 chunk。
4. 大量历史查询和 trace。

## 6. 测试数据生成原则

数据不是越随机越好。好的测试数据要有业务规律。

例如：

1. 节假日收入升高。
2. 某地区退款率异常。
3. 新产品上线后收入增长。
4. 某渠道转化率下降。
5. 文档里有对应业务原因。

这样系统才能展示“查数 + 找原因 + 给证据”的能力。

本地 small seed 还必须包含确定性的多年份月度收入 read model。至少
`business.revenue_by_month` 要覆盖 2011 到 2025 的每个月，并保留当前
2026 demo 月份。用户询问某个具体收入年份时，SQL 规划和答案合成都必须只
过滤到这个年份。系统不能用 2012 或 2026 的 rows 回答 2011 的问题。

## 7. 数据质量校验

Seed 后需要自动校验：

1. 表是否有数据。
2. 外键是否完整。
3. 指标是否能算出合理结果。
4. embedding 数量是否等于 chunk 数量。
5. 不同租户之间是否没有数据串联。
6. 按年份询问收入时，返回 rows 的 `month` 必须都以请求年份开头，并且
   evidence anchor 也必须引用同一个年份。

## 8. 实施顺序

1. 明确最终业务 demo 场景。
2. 设计业务表和文档表。
3. 加 migration。
4. 写 small seed。
5. 写 medium/large seed。
6. 加数据质量检查脚本。
7. 把 seed 接入 CI 或本地验证命令。
