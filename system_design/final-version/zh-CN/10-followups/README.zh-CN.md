# 10 后续设计：RAG 隔离、分享、保留、对话记忆、路由与提升持久性、混合文件回答、跨轮次 SQL 污染、文件分支相关性判断

English: [../../en/10-followups/README.en.md](../../en/10-followups/README.en.md)

这十四篇文档是对 [10 用户文件上传与混合数据分析](../10-user-file-upload-and-hybrid-analysis.zh-CN.md) 的延伸：前四篇来自实现完成后的复盘评审——在 RAG 知识库里发现的一个真实跨租户数据泄露问题、一套修正后的分享/治理模型、一个更符合"工作集而非存储"定位的保留模型，以及一个面向追问场景的对话记忆设计；第五篇来自对前四篇实现结果做 Docker 端到端验证时发现的两个额外缺陷；第六篇是针对 10.5 有意留白的一个缺口做的前瞻性设计；第七到第十一篇都来自对用户反馈的 bug 做的真实容器复现，或者本项目自己写测试的过程中在实现期间抓到的一次真实回归/偏差：第七篇发现 10.4 的对话历史注入机制，让某一轮的取值格式渗进了另一轮的 SQL 生成结果里；第八篇发现只要附带了文件，不管跟问题相不相关，都会被强行送进只从文件回答的那条路径；第九篇补上了第八篇那道判断自己留下的一个具体缺口——最初提议的补丁思路，拿报告里那个问题一验证，发现方向反了；第十篇补上了第八篇那道判断留下的第二个缺口，实现过程中也被自己最初的版本坑了一次——回归了第九篇的测试；第十一篇补上了第三个、也是最后一个缺口，自己的验收标准在写端到端测试时也需要修正一次——触发问题的那个场景，实际数据走的分支，跟设计最初假设的不一样。第十二、十三篇来自同一次分析师对正在运行的系统做实测的会话，不是一张 bug 工单：一份回答的截图里同时暴露出两个问题——证据不管相不相关都被渲染出来，以及一次 0 行的 join 结果被叙述成了一个确凿的"没有差异"结论（第十二篇）；一个纯只读的解释类问题，被一条把拦截原因说成"数据修改尝试"的 guardrail 消息挡了下来（第十三篇）——两篇都先写了设计和 Spec，然后实现完成。第十四篇补上了第十二篇留下的一个残留缺口：拿报告里那个原始对比问题重新实测时，依然复现了原来的 bug——先是因为跑着的 Docker 容器还是修复前的旧镜像，重新构建之后，又发现第十二篇那道"零行 join 提示"只在生成的 SQL 里出现字面 "join" 这个词时才会触发，而模型被要求"对比并标出差异"时完全可能改用 `EXCEPT` 写法，绕开了这道检查。

按下面的顺序读，每一篇都建立在前一篇的概念之上：

1. [10.1 RAG 按用户隔离](01-rag-per-user-isolation.zh-CN.md)——修复知识库里一个已确认的跨租户数据泄露问题；引入"基础知识 vs. 个人知识"两层划分。
2. [10.2 文件分享审批流程](02-file-sharing-approval-workflow.zh-CN.md)——把"admin 主动提升"改成"分析师申请、admin 审批"、分享给同角色同事的流程；批准分享作为其中一个后果，会顺带扩大 10.1 里的 RAG 可见范围。
3. [10.3 文件保留、自动归档与重新上传去重](03-file-retention-and-archival.zh-CN.md)——缩短保留期，把破坏性的过期清理改成"重新上传即可恢复"的归档模式，并把归档跟 10.1 的 RAG 可见性联动起来。
4. [10.4 多轮对话记忆](04-multi-turn-conversation-memory.zh-CN.md)——为 SQL 生成、RAG 检索、答案综合提供按会话隔离的对话上下文；文件附件在同一会话内跨轮次延续，追问完全靠消息历史解析，不设单独的改写步骤。
5. [10.5 纯文档问答路由与知识库提升的持久性](05-rag-only-routing-and-promotion-durability.zh-CN.md)——修复"纯文档问题被强制先过 SQL 关"的路由缺陷，以及"知识库提升可能悄悄生成空文档"的数据完整性缺陷。
6. [10.6 混选结构化/非结构化文件时的混合回答](06-hybrid-file-answering-for-mixed-selections.zh-CN.md)——对用户自己附带的非结构化文件做请求范围内的 RAG 检索，跟结构化文件的 SQL 查询结果合并成一个综合回答，补上 10.5 有意留白的那个缺口——10.5 做到的是"不崩溃"，还没做到"答对"。
7. [10.7 文件/联邦查询 SQL 生成中的跨轮次取值格式污染](07-cross-turn-value-format-contamination-in-file-sql-generation.zh-CN.md)——历史轮次里的取值格式（比如一条无关业务表回答里的英文月份名）可能渗进文件查询生成的 `WHERE` 子句里，产出"合法但为空"的 SQL 而不是一个错误；修复方式是加一条明确的 prompt 指示，再配合一个文件分支专属、更窄的对话历史窗口。
8. [10.8 路由进文件分支之前，加一道问题相关性判断](08-question-relevance-gate-before-file-branch-routing.zh-CN.md)——附带的文件（可能是前一轮遗留下来的选择）会强行把每一个问题都送进 FileDataAgent/FederatedQueryAgent，不管相不相关，产出一个信心满满的错误答案，或者一个赤裸裸的 SQL 报错，请求根本没机会走到主编排器那些真实的业务表；修复方式是加一道不调用 LLM 的词元重合度相关性判断，并刻意向"让真正的追问留在文件分支"倾斜。
9. [10.9 给相关性判断加一道业务数据信号安全网](09-data-domain-signal-safety-net-for-the-relevance-gate.zh-CN.md)——10.8 那道纯靠词元重合度的判断，单独用会误伤一个确实跟文件相关、但用了 schema 里没有的业务同义词表述出来的问题；修复方式是拿 `QuestionClassifier` 已有的业务数据关键词信号，去交叉验证"不相关"这个判断结果——而最初提议的那个交叉验证方案，一检查就发现对报告里那个问题本身是反的。
10. [10.10 混选场景下按单个文件做相关性过滤](10-per-file-relevance-filtering-in-mixed-selections.zh-CN.md)——把 10.8 那个按单文件判断的函数，扩展用来过滤混选场景里的 `structured_ids`，而不只是给整个请求做一次性的门禁，补上"一份不相关的结构化文件，跟一份相关的非结构化文件混在一起时，依然会被送进 FileDataAgent"这个残留场景；这道过滤刻意只在附带了非结构化文件时才生效——最初无条件运行的版本，回归了 10.9 自己的安全网。
11. [10.11 给文件 SQL 生成的 schema 上下文带上取值样本](11-value-sample-aware-schema-context.zh-CN.md)——10.8/10.9 自己做实盘验证时发现的一个"表亲问题"，跟 10.7 的失败模式类似：直接打在当前这一轮问题里的自然语言日期表述（不是从历史带过来的），依然可能被翻译成一个跟文件真实存储格式对不上的字面量，因为 SQL 生成用的 schema 上下文只有列名和类型，从来没有列的实际取值样本；修复方式是在文件上传时算一次取值样本，渲染进 SQL 生成的 prompt 里。
12. [10.12 混合文件/数仓对比回答的证据相关性过滤与 Join 不匹配提示](12-evidence-relevance-and-join-mismatch-caveats.zh-CN.md)——一个 RAG 关键词的单词误判（"internal"）把两篇不相关的文档拉进了一次文件对比回答的"Sources"列表，而且没有任何相关性下限能拦住它们；`FederatedQueryAgent` 的一次 join 因为 join key 不匹配而返回了 0 行，却被叙述成一个确凿的"没有差异"结论——在代码层面，这跟真的比较过、确实没有差异是完全无法区分的；修复方式是在证据被渲染出来的那一刻加一道相关性分数下限，再加一个 `zero_row_join_caveat` 信号，当一条包含 `JOIN` 的查询在数据源非空的情况下返回空结果时，把这个信号传给答案合成环节——这道下限的具体数值在实现过程中被修正过一次(见 10.12 自己的第 9 节),原因是实测发现它会误伤一篇既有测试已经覆盖的、真正相关的文档。
13. [10.13 为非 SELECT 类 LLM 输出保留 Guardrail 拒绝原因](13-guardrail-deny-reason-preservation.zh-CN.md)——"确实命中了真实的 DML/DDL 关键词"和"模型压根没生成 SQL"这两种情况被合并成了同一个 `SqlValidationViolationCode`，在传到前端的路上又被连续折叠了两次，导致一个针对某个 schema 里根本没有对应表的指标提出的、纯只读的"解释一下 X 是怎么算出来的"问题，被一条声称存在数据修改尝试的消息拦了下来；修复方式是新增一个违规代码、一个 `ErrorCode`、一个 `ApiErrorCode`，把这个区分原样带到前端，展示如实描述发生了什么的消息。
14. [10.14 把"零行 Join 提示"的比较查询判断，扩展到字面 JOIN 语法之外](14-comparison-query-detection-beyond-literal-join.zh-CN.md)——补上第 10.12 篇留下的一个残留缺口：它的 `zero_row_join_caveat` 只在生成的 SQL 里出现字面 "join" 这个词时才会触发，但一个被要求"对比并标出差异"的模型完全可以改用 `EXCEPT` 或 `NOT EXISTS`，照样能绕开这道检查，让原来那个"没有差异"的错误结论重新出现；修复方式是改成检查这条查询是不是真的同时引用了两个数据源视图，不管它用的是哪种 SQL 写法。

## 现状

这十四篇全部已实现并验证——10.12 和 10.13 按本项目通常的 SDD+TDD 顺序先写 Spec、再实现(各自 Spec 的第 9/10 节记录了实现过程中发现的修正)。10.4 里原本留白的两项（文件附件是否跨轮次延续、追问怎么解析）已经拍板：文件附件按会话延续（方案 A），追问完全依靠消息历史解析，不设单独的显式改写步骤（方案 B）。10.5 记录的两个修复是在对 10.1–10.4 做本地 Docker 端到端验证时发现并当场修复的，不是预先设计后再实现的。10.6 先按本项目通常的 SDD+TDD 顺序写成了前瞻性设计，之后转化成了 [Spec FV10.6](../../../../spec/final-version/zh-CN/10-followups/06-hybrid-file-answering-for-mixed-selections.spec.zh-CN.md) 并实现完成；准确的需求措辞以那份 spec 为准，实现过程中修正过两次（见 10.6 自己的第 9 节）。10.7、10.8、10.9 都跟 10.5 一样，是在带真实 LLM provider 的运行中 Docker 环境上实际复现后发现并修复的，不是提前设计的。10.7 记录了排查过程中一并发现、但有意留给未来后续文档处理的两个相邻缺口（见 10.7 自己的第 6 节）。10.8 自己的相关性判断函数，在实现过程中也被本项目的测试套件抓到过一次回归、又修正了一次（见 10.8 自己的第 5 节）——它自己的第 6 节记录了另外三个留白的缺口。10.9 关上了这三个缺口里的第一个，而它自己最初提议的方案，拿报告里那个问题一验证，就发现路由方向是反的（见 10.9 自己的第 3 节）——这次修正发生在任何代码写出来之前，比 10.8 被测试套件抓到回归的时间点还要早一步。10.10 按本项目通常的 SDD+TDD 顺序写完并实现了（先写 Spec FV10.10，再红后绿地实现）——但它自己最初、无条件版本的过滤，用的是跟 10.8 那个月份名词元缺口一样的方式被抓到的：靠跑全量测试套件，不是提前拿单一案例去检查（见 10.10 自己的第 4 节）。10.11 关上了第三个、也是最后一个缺口，按同样的顺序写完并实现了——但它需要修正的时间点，比 10.9 或 10.10 都要更早：就在写端到端测试的夹具数据时，那条测试还从来没有真正跑过，就已经发现触发问题的那个场景，它自己那一列 6 个取值走的是 `sample_values` 分支、还会被 `SAMPLE_SIZE` 截断，不是设计原本假设的 `sample_range` 分支——测试用的假 LLM client 因此被重新设计成"看格式揭示与否"而不是"看目标字面量在不在"，之后又拿真实 LLM 确认过这个设计是靠谱的（见 10.11 自己的第 4 节）。10.12 和 10.13 都是通过直接阅读某一次真实回答的响应实际走过的代码路径发现的，不是重放某一次具体的 LLM 调用；两者都按 FV10.6 的顺序先写了 Spec。10.12 自己也需要一次修正:在写相关性下限第一条测试数据的时候被发现——对照 `InMemoryKnowledgeStore` 真实的评分行为实测,最初提议的 `0.35` 下限会排除掉一篇既有测试已经覆盖的、真正相关的文档,同时又放行了报告里那个 bug 本身那两篇不相关文档的复现版本,于是这道下限被降到了 `0.15`,保住了既有测试通过,代价是不再能可靠地排除那类噪音(见 10.12 自己的第 9 节)。

10.14 走的是 10.5、10.9 那种"先实现、后补文档"的顺序，不是 FV10.6 那种"先写 Spec"的顺序——它自己的缺陷也是靠实盘复现发现的，不是提前设计出来的。拿触发 10.12 的那个原始问题重新做实盘复测时，在 10.12 的修复已经落进源码树之后，依然复现了原始 bug——先是因为跑着的 Docker 容器还是修复前构建的旧镜像（这是一个部署缺口，不是代码缺口：`Dockerfile.backend`/`Dockerfile.worker` 是在构建时把源码拷进镜像的，所以必须重新构建、重启才能生效），修正这一点之后，又发现 10.12 的 `zero_row_join_caveat` 触发条件是靠生成的 SQL 里有没有字面出现 "join" 这个词——而一个被要求"对比……并标出差异"的模型完全不需要一定写 `JOIN` 语法，改用了 `EXCEPT`，直接绕开了这道检查。10.14 把这道字面关键词检查换成了"这条查询是不是真的同时引用了两个数据源视图"，并针对一个重新构建过的 Docker 部署、用真实的 `gpt-4o-mini` LLM client 做了验证，确认返回的是修正后的 join 不匹配提示，而不是原来那个错误的"没有差异"结论（见 10.14 自己的第 4 节）。
