# 10.4 多轮对话记忆

## 1. 解决的问题

现在 `POST /api/v2/chat/query` 的每次请求都是独立回答的——SQL Agent、RAG Agent、文件相关 Agent 都看不到同一个会话里之前问过什么。一个追问，比如"那七月份呢？"，根本没法被正确理解：没有任何东西把"我们刚才在聊营收"这件事从上一轮带到这一轮。本文档设计的是按会话（session）隔离的对话记忆，类似 ChatGPT/Claude 的体验：一个 session 是一条连续的对话线程，开一个新 session 就是开始一段全新的、不相关的对话。

## 2. 已经具备的基础

`session_id` 现在其实已经贯穿了整条链路——每个 `QueryRequest`、每条 `QueryHistoryRecord`、每条审计记录都带着它，而且前端本来就是每个浏览器标签页生成一个 `session_id`，这一整个标签页里问的所有问题都复用同一个（`App.tsx` 里的 `useRef(newSessionId()).current`）。缺的不是这个标识符本身，而是（a）一种"按 session_id 取出之前几轮对话"的方式，以及（b）在生成下一个回答时**真正用上**这些历史。

## 3. 取出会话历史

`InMemoryQueryHistory`（`src/chatbi/history/in_memory.py`）现在只能按 `trace_id` 查，没有按会话查询的能力。给它加一个方法：

```python
def list_by_session(self, session_id: str, *, limit: int = 5) -> tuple[QueryHistoryRecord, ...]:
    """取这个 session 最近 N 轮，按时间从旧到新排列。"""
```

`limit` 用来限制上下文窗口大小——为什么必须有限制而不是"整个会话全带上"，见第 5 节。

## 4. 上下文要塞进哪几处

有三个调用点需要历史信息，各自的理由不一样：

| 调用点 | 为什么需要历史 | 需要历史里的什么内容 |
|---|---|---|
| SQL / DuckDB SQL 生成（`sql_agent`、`FileDataAgent._generate_sql`、`FederatedQueryAgent._generate_sql`） | 把"那七月份呢？"补全成一个完整、自包含的问题，再去生成 SQL | 之前的**问题**（最好还有当时解析出的指标/表），不需要完整答案 |
| RAG 检索 | 检索用的查询文本本身需要把指代词还原（"那个"→"七月营收下滑"），才能查到对的文档 | 之前的问题 + 上一次回答的简短摘要 |
| 答案综合（`GroundedAnswerSynthesizer`） | 回答应该读起来像是接着说，而不是把用户已经知道的上下文再复述一遍 | 之前的问答对，原文或轻度截断均可 |

**已确定**：把最近 `limit` 轮历史格式化成普通的 `{"role": "user", ...}`/`{"role": "assistant", ...}` 消息，拼在这条链路本来就会发起的每次 LLM 调用最前面。不设单独的"问题改写器"这一步——`sql_agent`、`FileDataAgent._generate_sql`、`FederatedQueryAgent._generate_sql`、RAG 检索、`GroundedAnswerSynthesizer` 都直接从拼进去的消息历史里自己解析指代/省略引用，就跟一个人读同一份对话记录理解上下文一样。如果之后实际用起来发现某类追问处理得不够好，那是对这个决定的后续修订，不是这份文档里留的一个悬而未决的口子。

## 5. 上下文窗口

历史不能无限制地带——每多一轮，token 成本和延迟都会涨，而且很久以前的轮次通常跟当前问题已经没关系了。建议：最近 **5 轮**（对应上面 `limit` 的默认值），只带问答对本身（不带完整的证据列表/表格数据）——这是个起始值，等观察到真实使用情况后再调，不是硬性要求。

## 6. 文件是否跨轮次"粘连"——已确定

**已确定：文件附件在一个会话内跨轮次延续（方案 A）。** 如果第一轮勾了 `file_ids=[X]`，第二轮追问没有再传 `file_ids`，系统会继续用文件 X——用户不需要每一轮追问都重新勾选同一个文件，符合这次功能想要的"像 ChatGPT"的目标。

实现机制：这**不是**靠扫描第 5 节里那个有限的对话上下文窗口来实现的（一个会话围绕同一个文件聊的轮次，完全可能比上下文窗口保留的轮数多得多）。而是每个会话单独维护一小块专门的状态——该 `session_id` 下最近一次**显式**传入的非空 `file_ids`——这块状态跟"当前往 LLM prompt 里注入多少问答历史"完全独立：

- 一次请求如果显式传了非空 `file_ids`，永远使用这个值，并且把它设为该会话之后的"当前生效" `file_ids`。
- 一次请求如果 `file_ids` 为空/没传，就沿用该会话当前生效的 `file_ids`（如果有的话），并且按跟客户端显式传了一样的方式，走文件查询这条分支。
- 如果一个会话里从来没有显式附过任何文件，那么空 `file_ids` 的请求就真的当作没有文件处理——没有可以继承的东西，跟现在一样走主编排器。
- 这个契约里有意不设计一个单独的"取消这个文件"信号——会话中途想不再用某个文件，唯一的办法是显式传一个不同的（或者以后产品加了明确的"清除"操作再传空的）`file_ids`，或者直接开一个新会话（见第 7 节）。

这是对 `_handle_file_data_chat_query` 和主编排器之间路由判断（见 [FV-10](../10-user-file-upload-and-hybrid-analysis.zh-CN.md)）的一次真正的行为改动——一次请求走哪条分支，现在取决于会话状态，不再只取决于这次请求自己的请求体。

## 7. 前端改动

- 把"每次回答覆盖上一条"改成在当前 `session_id` 下追加、可滚动的对话线程。
- 加一个"开新对话"的操作，生成一个全新的 `session_id`，清空当前可见的线程（旧会话的历史仍然可以通过现有的聊天历史接口查到，什么都不会被删除）。
- 按第 6 节已经确定的方案，文件面板的勾选状态应该改成"作用域是这个 session"，而不是"一直选中直到手动取消"——前端开一个新对话（新会话）的时候，也应该把可见的文件勾选状态一并清空，这样界面上就不会出现"看着像勾了文件，但后端这个新会话其实压根没有生效文件"的错位情况。
